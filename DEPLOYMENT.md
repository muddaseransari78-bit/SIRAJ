# Deploying SIRAJ (step by step)

## Fastest ways (Phase 23)
- **One command on your own PC (Docker):** see section 6 below. Good for a final test before going online.
- **Render Blueprint:** `render.yaml` in the project root creates the backend for you (secrets are generated by Render). You only paste `MONGO_URI` and `CLIENT_URL`.
- **Make your own strong secrets:** `cd backend` then `npm run secrets` (prints two different values).
- **After deploying, check everything:** `npm run deploy-check` (section 5 below).

Recommended free-tier setup: **MongoDB Atlas** (database) + **Render** (backend) + **Vercel** or **Netlify** (frontend).
Other hosts work the same way. Do the steps in this order.

## 1. Database (MongoDB Atlas)
1. Create a free cluster, a database user, and under *Network Access* allow `0.0.0.0/0` (Render has no fixed IP).
2. Copy the connection string (`mongodb+srv://...`). URL-encode special characters in the password (`@` -> `%40`).

## 2. Backend (Render "Web Service")
- Root directory: `backend` - Build command: `npm install` - Start command: `npm start`
- Environment variables (Render -> Environment):

| Name | Value |
|---|---|
| `NODE_ENV` | `production` |
| `MONGO_URI` | your Atlas string |
| `JWT_ACCESS_SECRET` | long random text (40+ characters) |
| `JWT_REFRESH_SECRET` | a DIFFERENT long random text |
| `CLIENT_URL` | your frontend address, exactly, e.g. `https://siraj.vercel.app` (no trailing `/`) |
| `COOKIE_SAMESITE` | `lax` (the site reaches the API through its own `/api` address, see section 3) |
| `TRUST_PROXY` | `2` (Vercel + Render = two proxies; use `1` if the frontend calls Render directly) |

- Test: open `https://YOUR-BACKEND.onrender.com/api/health` -> "SIRAJ API is running". Then `/api/health/ready` -> "SIRAJ API is ready" (it answers 503 while MongoDB is not connected, so it is the right address for Render's health check and for an uptime monitor).
- With the Blueprint (`render.yaml`): Render -> New + -> Blueprint -> choose your repo. Everything in the table above is filled except `MONGO_URI` and `CLIENT_URL` (you type those) - the two JWT secrets are generated.
- Create the first admin: in the Render shell (or locally with the same `MONGO_URI`) run `npm run seed`, log in, and **change the password immediately** (Profile page).
- Free Render services sleep after inactivity; the first request can take ~30 seconds.

## 3. Frontend (Vercel or Netlify)
- Root directory: `frontend` - Build command: `npm run build` - Output directory: `dist`
- First put your real backend address in `frontend/vercel.json` (replace `REPLACE-WITH-YOUR-BACKEND.onrender.com`) - a Vercel build stops with a message if it is still the placeholder.
- Environment variable: `VITE_API_BASE_URL` = `/api`
  (it is baked in at build time - after changing it, redeploy).
- `vercel.json` and `public/_redirects` are already included so refreshing a page like `/quran/2` works.

### iPhone / Safari: why the site calls `/api`
Safari (and more and more Chrome settings) block the login cookie when the site and the backend are on **different domains** (e.g. `siraj.vercel.app` + `siraj-api.onrender.com`). Then a visitor is logged out after 15 minutes. So SIRAJ lets the site and the API share ONE address: `vercel.json` passes `/api/...` on to Render, the browser only ever talks to the Vercel address, and the cookie is first-party.
- `frontend/vercel.json` second rewrite: `{ "source": "/api/:path*", "destination": "https://YOUR-BACKEND.onrender.com/api/:path*" }` (the SPA rewrite before it skips `/api/`, so order is safe).
- `VITE_API_BASE_URL` = `/api`, `COOKIE_SAMESITE` = `lax`, `TRUST_PROXY` = `2`, `CLIENT_URL` = your site address.
- **Netlify instead:** put `/api/*  https://YOUR-BACKEND.onrender.com/api/:splat  200` FIRST in `frontend/public/_redirects`.
- A custom domain with the backend on a sub-domain (`api.yoursite.com`) works too.

## 4. After deploying - checklist
- [ ] Register, log in, close the browser completely, open the site again - you are still logged in (also true after days away, up to 90 days) (if not: check `CLIENT_URL` and `COOKIE_SAMESITE=none`).
- [ ] Open `/quran/1`, `/prayer` (allow location), `/admin` as admin.
- [ ] No browser console CORS errors and no "Refused to ..." (CSP) errors.
- [ ] Security headers present (`npm run deploy-check` tests this).
- [ ] Chrome menu -> "Install SIRAJ" appears (needs HTTPS).
- [ ] `JWT_*` secrets and the database password appear nowhere in the frontend or in git.

## Security reminders
- Never commit `.env`. Rotate any secret that was ever pasted into chat or git.
- Rate limits are active on the whole API (300/min per visitor), and stricter on login/register, password change, session refresh, search and the Source Finder. Set `TRUST_PROXY=1` on Render/Railway or every visitor looks like the same IP.
- In production the backend refuses to start with example, short (< 32 characters) or identical JWT secrets. Make one: `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"` (run it twice, one value per secret).
- The frontend ships security headers (Content-Security-Policy etc.) in `frontend/vercel.json` (Vercel) and `frontend/public/_headers` (Netlify). After deploying, open the site, press F12 -> Console and check there is no "Refused to ..." message. To tighten the policy, replace `https:` in `connect-src` with your backend address in BOTH files.
- Logout only clears the cookie in that browser. A stolen refresh token stays valid until it expires (90 days, renewed each time the person comes back). If you ever suspect a leak, change `JWT_REFRESH_SECRET` and redeploy: everyone is logged out.
- Server errors are saved (without request data) and visible in Admin -> Error Logs for 30 days.
- Back up the database (Atlas has scheduled backups on paid tiers; on free tier export occasionally).

## 5. Automatic check after deploying
In PowerShell (Node 18+), from the `backend` folder:

```powershell
cd D:\SIRAJ\backend
$env:API_URL="https://YOUR-BACKEND.onrender.com"
$env:SITE_URL="https://YOUR-SITE.vercel.app"
npm run deploy-check
```

It only reads (creates nothing). It checks: API alive and ready, standard 404 and no stack trace, security headers, CORS (your site allowed, a stranger not), the site's headers, `/quran/2` after refresh, manifest and service worker. Expected: `NN passed, 0 failed`. A `FAIL` line tells you which setting to look at (for example CORS -> `CLIENT_URL`).
For a free Render service, run it twice: the first call wakes the server up.

## 6. Run everything with Docker on your PC (optional)
Needs Docker Desktop.

```powershell
cd D:\SIRAJ
copy .env.docker.example .env.docker
cd backend ; npm run secrets ; cd ..
# paste the two secret lines into .env.docker, and set SEED_ADMIN_PASSWORD to a strong password of yours
docker compose --env-file .env.docker up --build
```

Open http://localhost:8080 . Create the first admin in a second window:
`docker compose --env-file .env.docker exec backend node scripts/seed.js`
Stop with Ctrl+C; your data stays in the `mongo-data` volume (`docker compose down -v` deletes it).
Notes: MongoDB is not reachable from outside the containers. The compose file runs the backend in production mode, so it refuses weak secrets. If login does not stay after refresh in Safari, use Chrome or Edge for this local test (Safari is strict about secure cookies on http).
Both images can also be used on any container host (Railway, Fly.io, a VPS): `backend/Dockerfile` and `frontend/Dockerfile` (the frontend one takes `--build-arg VITE_API_BASE_URL=https://YOUR-API/api`).

## 7. Continuous checks (GitHub)
`.github/workflows/ci.yml` runs the backend tests, frontend tests, the production build and the Python tests on every push and pull request. Push the project to GitHub and open the *Actions* tab. A red cross means a test or the build failed - click it to see the first error.

## Not covered here
Custom domain, email sending, monitoring/alerts, and load testing. (Web Push for prayer reminders: see section 8.)

## Optional: zabar / zer / pesh check (pronunciation service)
Only needed if you want the "Also check zabar / zer / pesh" option in Live Recitation. Without it the rest of SIRAJ works exactly as before.
1. Deploy `pronunciation-service` as its own service (needs Python 3.10+, `ffmpeg`, `torch`; CPU works for testing, a GPU host is better for many users). Set `API_KEY` (long random text). `MODEL_ID` defaults to `tarteel-ai/whisper-base-ar-quran` (a Quran Whisper model that writes harakat); see `pronunciation-service/README.md` for the bigger option and `try_model.py` to test a model first.
2. On the backend add `PRONUNCIATION_API_URL` (the service address, HTTPS in production) and `PRONUNCIATION_API_KEY` (same as `API_KEY`). Redeploy.
3. Check: `https://YOUR-SERVICE/health` answers, then log in, open Recite Live and tick the new option. If the page says "Could not check: ... plain letters", the model does not write harakat.
- Every check costs compute. The check after each Ayah is limited to 12 per minute per IP; the LIVE check (about one request every 1.5 s while a user recites) to 90 per minute per IP. A small model on CPU can serve one reciter at a time; for many users you need a GPU host. Watch your host's usage.
- Free hosts that sleep make the first check slow (the backend waits up to `PRONUNCIATION_TIMEOUT_MS`, default 60 s).

## 8. Prayer reminders when the site is closed (Web Push, Phase 31)
1. Make the keys once: `cd backend` then `npm run vapid`. It prints `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` and `CRON_SECRET`.
2. Paste them into `backend/.env` (local) or Render -> Environment (never into git). Keep the SAME pair forever: a new pair means every device must turn the option on again. Redeploy. The log shows `Push scheduler running`.
3. The site must be **https** (the Vercel / Netlify / Render addresses are). On iPhone the user must first use *Share -> Add to Home Screen*.
4. **Free hosts sleep.** A Render free web service stops after about 15 minutes without visits, and a sleeping server cannot send a reminder. Fix: make a free timer at cron-job.org (or UptimeRobot) that opens `https://YOUR-BACKEND/api/cron/prayer-tick?secret=YOUR_CRON_SECRET` every 5 minutes (or sends the header `x-cron-secret`). It keeps the server awake AND runs one reminder check. For reminders you can fully rely on, use a paid always-on plan.
5. Check: log in -> Prayer page -> turn Reminders On -> *Send test from server*. Close SIRAJ and the notification should still appear.


## 9. Google and Apple sign-in (REMOVED from the website in Phase 41 - this section is only for the unused backend code)
Email login works without any of this. A Google / Apple button appears on Login and Register **only when its id is set** (the page asks the backend which ones are on), so nothing half-working is ever shown to visitors.

### Google (about 5 minutes, free)
1. console.cloud.google.com -> create a project -> **APIs & Services -> OAuth consent screen** (External, fill name + email, publish it).
2. **Credentials -> Create credentials -> OAuth client ID -> Web application.**
3. **Authorised JavaScript origins:** add your site, e.g. `https://siraj.vercel.app` and, for testing, `http://localhost:5173`. (No redirect URI is needed.)
4. Copy the **Client ID** (ends with `.apps.googleusercontent.com`).
5. Backend (Render -> Environment): `GOOGLE_CLIENT_ID=<that id>`. Frontend (Vercel -> Environment Variables): `VITE_GOOGLE_CLIENT_ID=<same id>`. Redeploy both.

### Apple (needs a paid Apple Developer account, 99 USD / year)
1. developer.apple.com -> Certificates, Identifiers -> **Identifiers -> App IDs**: make an App ID and switch on *Sign in with Apple*.
2. **Identifiers -> Services IDs**: make one (e.g. `com.yourname.siraj.web`), switch on *Sign in with Apple* -> Configure: **Domains** = your site without https (e.g. `siraj.vercel.app`), **Return URLs** = your site address with https (e.g. `https://siraj.vercel.app`).
3. Backend: `APPLE_CLIENT_ID=<the Services ID>`. Frontend: `VITE_APPLE_CLIENT_ID=<same>` and `VITE_APPLE_REDIRECT_URI=https://siraj.vercel.app`. Redeploy both.
4. Apple does not work on `localhost`; test on the deployed https site.

How it is kept safe: the browser only receives a signed token from Google / Apple; the backend checks its signature with the provider's public keys, that it was made for YOUR id, that it is not expired, and that the one-time `nonce` matches. Only then is the account found / created. A person who first signed up with email and later uses Google with the same (verified) email gets the same account.

### Checks
- Login page shows the Google button (and Apple if set) and no phone option.
- Sign in with Google -> you land on the page you came from, the navbar shows your name, closing the browser and returning keeps you logged in.
- Console has no "Refused to load the script" (the CSP allows only `accounts.google.com/gsi/client` and `appleid.cdn-apple.com`).
